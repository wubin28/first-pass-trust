# 让Agent一次生成可信代码 V2.0：国内Token不自由开发者用SDD、DDD和Approved Scenarios维护非智能棕地软件项目

![cover-image-v2.3.png](cover-image-v2.3.PNG)

先问一个问题：**如何让 Agent 在有限的 token 预算下，第一次就生成可信的代码——不必靠反复来回试错去逼近正确答案？**

国内做 Agent 辅助编程的开发者，大多绕不开一个现实约束：token 不自由。国际大模型 API 访问受限、走中转遭“提示词中间人攻击”风险大、走本地私有化部署大模型成本高、企业内部又对调用量有配额——这些都意味着"多轮对话慢慢纠错"这条路走不通。可现实是，Agent 生成的代码常常"看着对、跑不对"：编译通过、逻辑读起来顺，但一提交测试就炸，或者悄悄改变了原有行为，甚至在[棕地项目](https://www.environmentalworks.com/what-is-a-brownfield-project/)（借用土木工程中的术语，指在老旧软件系统之上开发与部署新软件系统的项目）里悄悄破坏了看不见的既有契约。需要注意的是，这里说的"棕地项目"，并非所有"现存的软件系统"，仅指**需要长期维护的传统非智能软件**——并不包含正在开发中的有智能的 agent 系统。说白了，就是一个已经上线、有存量付费用户、有历史 API 契约的普通代码库。这种棕地项目恰恰是国内绝大多数开发者日常打交道的对象。棕地项目要维护、要兼容、要不破坏别人依赖的行为，Agent 一旦生成不可信代码，返工成本会成倍放大。

这就是本书要回答的唯一问题。

> 作者：伍斌，30 余年 IT 从业经验，曾在 Thoughtworks 任资深软件开发咨询师 8 年，专注用规范化的需求表达、测试驱动开发与 AI 编程工具的组合，帮助团队在棕地项目中安全、低成本地落地 AI Coding（完整介绍见下文"关于作者"）。

## 本书方法论：理解 → 设计 → 构建 → 评测，四元素闭环

回答"如何让 Agent 一次生成可信代码"这个问题，乍一看像是在喊一句口号，拆解开来，其实是一条可执行、可验证的四元素链路：

1. **理解**代码所承载的复杂业务逻辑——用 [DDD（Domain-Driven Design）](https://www.oreilly.com/library/view/learning-domain-driven-design/9781098100124/) 的 strategic design，把一个陌生棕地代码库拆成核心（core）、通用（generic）、支撑（supporting）子域，分清主次，再分析新需求会牵动哪些子域、哪些类。
2. **设计**面向验收测试的 spec——用 [Decision Table Testing（决策表测试法）](https://www.virtuosoqa.com/post/decision-table-testing) 从业务规则系统性地推导验收测试用例，保证不遗漏、不重复，不必靠直觉随手列几个例子凑数。
3. **构建**面向业务不变式的自动化验收测试——用 [Approved Scenarios](https://lexler.github.io/augmented-coding-patterns/patterns/approved-scenarios/) 模式（结合 TDD 的红绿重构节奏）针对不变的业务事实，把每一条验收测试用例落地为一份产品经理也能读懂的、Agent 真正执行的 markdown fixture，解决"Agent 生成的测试和生产代码都不可信"的问题。
4. **评测**自动化验收测试确实保护了生产代码——用 [Fault Injection Testing](https://www.geeksforgeeks.org/software-engineering/fault-injection-testing-software-engineering/)（故障注入测试）在生产代码里精心注入与每条测试保护意图语义对应的故障，验证测试确实会变红、报错信息确实对应，排除"测试形同虚设"的可能。

在 AI Coding 时代维护棕地项目，无论是开发新需求，还是修 bug，都离不开上述四个基本要素。

这条链路背后有一条共同的方法论：**理解、设计、构建、评测这四步探索未知或复杂问题的每一步开头，都用"假设体检+追问"风格的提示词来与 Agent 澄清诉求**——列出隐含假设、列出缺失信息、指出常见错误、只问最关键的问题——再给出带推荐理由的方案，拒绝上来就甩出一个看似权威、实则谁都能套用的通用答案。本书第 2～5 章的实操过程会反复示范这套"假设体检+追问"风格的提示词，这也是本书希望读者在自己的实践中养成的工作习惯。

本书以 [Apache Commons CSV](https://github.com/apache/commons-csv) 为唯一贯穿案例，用同一个新需求走完理解、设计、构建、评测四个环节。这个新需求是给 `CSVFormat.Builder` 新增 `setRequiredHeaders(String...)`，以便在解析时一旦发现 CSV 表头缺少这些列，就在读第一条记录之前抛出一个清楚说明缺了哪些列的错误，而并非等业务代码调用 `record.get("currency")` 时才报错。

## 30秒判断：这本书适合你吗？

**你适合读这本书，如果你：**

- 已经在用 Agent（如 Claude Code、Codex CLI 、OpenCode v2 、Pi、CodeBuddy 、Mimo 、Trae CN IDE等）写代码，并且已经踩过"Agent 生成的代码看着对、跑不对"这类坑；
- 日常维护的是一个**需要长期维护的传统非智能软件**——已经上线、有存量用户、有历史契约的普通代码库（公司内部系统、客户交付项目都算），而并非在开发 agent 系统本身；
- 国内 token 不自由，需要在有限调用预算下把 Agent 用出确定性结果，又用不起或不方便用国际闭源工具链。

**你可以放心读，即使你：**

- 还不太懂 DDD，也很少写自动化测试——本书并非 DDD 或测试教程，不要求你提前掌握这些；你会在一个真实棕地需求里，边做边学到足以约束 Agent 的最小必要概念与操作。

**你可能需要先做点准备，如果你：**

- 还没实际用过 Agent 辅助编程工具——建议先上手体验一段时间，再来看本书会更有共鸣。

**实操环境要求：**

本书不绑定任何特定工具和模型。全书每章结尾给出的提示词，发给你自己常用的、国内外口碑良好的任意 AI Coding Agent 搭配任意大模型都能跑通——例如 Claude Code 搭配 Opus 5.5、Codex CLI 搭配 GPT 6.1 Sol、OpenCode V2 搭配 GLM 5.3、Pi 搭配 DeepSeek v4 pro、CodeBuddy 搭配 GLM 5.3 等。全书实操以 **OpenCode v2 + DeepSeek V4.1 Flash** 为锚点组合（不需要国际信用卡、不依赖受限的国际网络访问，对国内 token 不自由的读者更现实）；实际撰写过程中的实战环节，主要使用了 **Claude Code 搭配 Sonnet 5** 。

## 给 v1.0 老读者：v2.0 核心升级

> 如果你读过本书 v1.0（《让AI一次生成可信代码：国内Token不自由开发者用Codex、Superpowers、EARS、SDD和TDD维护棕地开源项目》），这里说明 v2.0 带来了什么变化，方便你判断值不值得重新读一遍；如果你是第一次接触本书，这节可以跳过。

- **方法论从"四步通用流程"升级为"理解 → 设计 → 构建 → 评测"四个更系统化的环节**：v1.0 的"拆需求 → 出 spec → TDD 实现 → 频繁跑测试"是一条通用工程流程；v2.0 把每一步都换成了一套有明确方法论支撑、可独立验证效果的具体技法——用 DDD strategic design 理解代码、用 Decision Table Testing 设计验收测试、用 Approved Scenarios + TDD 构建自动化测试、用 Fault Injection Testing 评测这些测试是否形同虚设。每一步都给出了"没有它会怎样""独特优势是什么"的具体论证，不再停留在流程口号上。
- **工具链从"绑定 Codex + Superpowers"变为完全不绑定任何工具和模型**：v1.0 的实操深度依赖 Codex 和 Superpowers 这一套特定组合；v2.0 的每一条提示词**都不依赖任何 Skill 或特定工具链**，换成你自己常用的、国内外口碑良好的任意 AI Coding Agent 搭配任意大模型都能跑通，国内 token 不自由的读者不必再迁就某一家工具。
- **新增"动手练习"机制，每章结尾都有一份可以直接复制给你自己 Agent 的完整提示词**：v1.0 更偏向"展示提示词和产出摘要"；v2.0 把每章分散的提示词合并打磨成一份带占位符说明的完整可执行提示词，放在章末，鼓励你先自己跑一遍、再回头和本章的参考答案对比复盘，把"看懂"真正变成"做过"。
- **案例从"三个场景各自展开"收拢成"一个需求、贯穿四个环节"**：v1.0 用三个场景（开发新功能/修复缺陷/偿还技术债）分别演示四步法；v2.0 聚焦一个真实的 `commons-csv` 新需求，让理解、设计、构建、评测四个环节在同一个需求上逐层深入，每一步的产出都是下一步的直接输入，更接近真实棕地项目里"从拿到需求到交付可信代码"的完整链路。
- **读者画像从"棕地开源项目"扩展到"任何需要长期维护的非智能棕地软件"**：不再局限于开源项目，只要你维护的是一个已经上线、有历史契约的普通代码库（公司内部系统、客户交付项目都算），这套方法论都适用。
- **"假设体检 + 追问"的工作习惯贯穿全书**：每当遇到需要探索或裁决的开放问题，书里都先做一次假设体检、给出带理由的方案，而并非直接甩出一个看似权威的通用答案——这是 v2.0 新加入的方法论，也希望你能带进自己的工作习惯里。
