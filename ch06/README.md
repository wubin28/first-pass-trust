# 第六章 总结"让 Agent 一次生成可信代码"工程范式

如何把"让 Agent 一次生成可信代码"这套工程范式迁移到你自己维护的棕地项目中？

## 方法论回顾

全书用同一个新需求——给 `commons-csv` 的 `CSVFormat.Builder` 新增 `setRequiredHeaders(String...)`——走完了四个环节：

1. **理解**（第二章）：用 DDD strategic design 把代码库拆成核心、通用、支撑子域，再分析新需求会牵动哪些子域、哪些类、子域间的接口会发生什么变化，留下一批需求原文没讲清楚的开放设计问题。
2. **设计**（第三章）：先用轻量的 ADR 把开放设计问题逐一裁决，再用决策表测试法把裁决结果系统性地推导成一份不遗漏、不重复的验收测试用例清单。
3. **构建**（第四章）：用 Approved Scenarios 模式结合 TDD 的红绿节奏，把验收测试用例落地成人类可读、Agent 真正执行、能在 IDE 里逐条单步调试的自动化测试。
4. **评测**（第五章）：用故障注入测试验证这些测试确实在保护对应的生产代码，而不是形同虚设——每一处故障都与某条测试的保护意图语义对应，而不是机械的随机变异。

乍看像是四个各自独立的工具箱，细看才发现，是一条环环相扣的证据链：理解给出业务边界，设计给出系统性的验收标准，构建把验收标准变成受测试保护的代码，评测把"这些测试真的有用"变成可重复的证据。少了任何一步，前后的工作都会打折扣——没有理解就动手设计，决策表的条件容易找错地方；没有系统设计就直接让 Agent 写测试，容易遗漏或重复场景；测试写完不做评测，就永远不知道这些测试是真的有效，还是一批精心包装的空测试。

这条链路回应的是第一章提出的那个困境：国内 token 不自由的开发者，没有本钱靠多轮试错去逼近正确答案，又必须在充满隐性契约的棕地项目里工作。四元素方法论把"信任"从一句主观判断，变成了一条可执行、可验证、每一步都有事实依据支撑的工程流程——这正是"第一次生成就可信"真正的含义：与其指望 Agent 一次就蒙对，这套流程做的，是把"对不对"这件事，从依赖 Agent 的运气，变成依赖一套可复现的验证机制。

## 给 token 不自由开发者的行动清单

把这套方法论迁移到你自己维护的棕地项目，建议按下面的顺序检查：

1. **先画一张子域地图，再动手改代码**。哪怕只是花半小时让 Agent 帮你梳理一下"这个代码库里哪些类是核心业务逻辑、哪些是边角配置"，也比直接扎进代码细节更容易把改动范围划对。警惕"代码行数多=业务复杂"这个常见错觉。
2. **把"需求原文没讲清楚的问题"显式列出来，裁决它，再往下走**。不要把这些模糊点悄悄藏在 Agent 生成代码的某个隐含假设里——用一份轻量的 ADR 把它们摆到桌面上，每条决策配一个可追溯的理由，哪怕理由只是"和现有代码风格保持一致"。
3. **验收测试的设计，用决策表而不是直觉列举**。尤其当你发现"这个条件的结果好像要看另一个条件"时，这就是该用决策表、而不是简单罗列测试用例的信号。
4. **让测试本身可评审，而不是只有代码可评审**。用 Approved Scenarios 一类的模式，把"这个测试在验证什么"从一段断言代码，变成一份不需要懂代码就能看懂的结构化文档——这对需要让产品经理、测试、开发三方共同评审 Agent 产出的场景尤其重要。
5. **测试全绿之后，别急着收工，做一轮故障注入**。挑几个关键测试，精心设计几个与其保护意图语义对应的故障，验证"变红→报错对应→变绿"这个闭环，确认这些测试不是摆设。
6. **工具和大模型可以换，方法论不用换**。本书全程用 OpenCode + DeepSeek V4.1 Flash 做实操锚点，是为了贴合国内 token 不自由的现实约束，但四元素方法论本身不绑定任何特定工具——换成你自己常用的、国内外口碑良好的 AI Coding Agent 搭配大模型（如 Claude Code 搭配 Opus 5.5、Codex CLI 搭配 GPT 6.1 Sol、OpenCode V2 搭配 GLM 5.3、Pi 搭配 DeepSeek v4 pro、CodeBuddy 搭配 GLM 5.3 等），应该同样适用。
7. **每一步遇到不确定、需要判断的地方，先做"假设体检"再动手**：列出隐含假设、列出缺失信息、指出最容易犯的错误、只问最关键的问题——这个习惯比记住某个具体工具的用法更重要，它能迁移到任何你将来会遇到的新需求、新代码库上。

## 展望

全书用一个相对典型、体量适中的需求走完了四元素方法论的完整闭环，但真实的棕地项目远比这个案例复杂——可能涉及跨团队协作、历史遗留的技术债、更大体量的代码库。这些更复杂的场景不会让四元素方法论失效，但会让每一步的工作量和不确定性都更大：子域地图可能需要分好几次迭代才能画清楚，开放设计问题可能牵涉到多个团队的既有约定，决策表可能需要拆成更多张互相关联的子表，故障注入的范围也需要更谨慎地取舍。

如果你在自己的项目里尝试了这套方法论，不管是顺利跑通了，还是在某一步卡住了、和书里的参考答案出现了分歧，都值得记录下来——这些分歧往往比"方法论讲得对"这件事本身更有价值，因为它们会告诉你，这套方法论在你的具体处境里，哪里需要调整、哪里可以直接照搬。这正是本书从第一章到第五章反复邀请你"自己动手、再和参考答案对比复盘"的用意：方法论最终要为你的真实工作服务，不是用来背诵的教条。
