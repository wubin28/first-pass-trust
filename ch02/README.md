# 第二章 理解代码所承载的复杂业务逻辑

按照本章后面的提示词在你自己的 Agent 上实操一遍后，你将学会用单步调试和 DDD strategic design 快速理解一个陌生棕地代码库、分清核心业务逻辑与边角配置，并精确定位新需求会牵动哪些子域和类。

你接手了 `commons-csv` 这个陌生代码库，这个代码库需要你长期维护。最近你需要添加 `required headers` 新需求，你会如何在 Agent 的帮助下快速理解这个项目的软件架构，以便顺利添加新需求？

本章会用 DDD（Domain-Driven Design）的 strategic design 方法，带你走一遍"理解陌生棕地代码库、分清主次、分析新需求影响范围"的完整过程。

> [!TIP]
> **TL;DR · 读完本章你会：**
> - 学会先用单步调试代码库里现有的自动化验收测试，亲眼核实 AI 讲的代码行为是不是真的在代码里发生；
> - 学会用 DDD strategic design 把一个陌生棕地代码库拆成 core / generic / supporting 子域，分清哪里值得细读、哪里扫一眼接口就够；
> - 看到这套方法套在 `commons-csv` 上的真实判定结果——格式契约、解析编排与表头/记录语义是 core，词法读取机制是 generic，格式写出编排、错误词汇是 supporting；
> - 学会识别"代码行数大≠业务逻辑复杂"这个最容易踩的坑；
> - 看到 `required headers` 新需求如何被精确定位到该落脚的子域和类，而非凭直觉改动。

## 2.1 热身阶段单步调试指南：用现有行为的测试理解 commons-csv

> [!NOTE]
> 本节内容对应困境二——AI 讲的架构、时序图听起来很有道理，但哪些是真的在代码里发生的，光听转述说不清。在正式用 DDD strategic design 拆子域之前，先亲手单步调试一遍代码库里现有的验收测试，把"听 AI 说"换成"亲眼看代码真的怎么跑"。下面并非 Agent 产出文档的全文，而是我把本章 2.5 节的"热身提示词"发给 OpenCode V2 搭配 GLM 5.3 之后，真实发生的问答过程、产出清单与可信度验证方式的复盘。建议你先快速浏览完这一节，再去跑 2.5 的提示词，跑完回来对照看看你的 Agent 给出的问题和产出有什么不同——我不会在这里重复讲 commons-csv 的内部实现，因为那样会搅乱你自己跑提示词后理解 Agent 与你的互动以及所生成的文档时的亲身体验。

### 过程：Agent 问了什么，我怎么答的

我发给 Agent 的这份热身提示词，大致是这样安排的：先给它定了个身份——一名熟悉 JUnit 5、也熟悉用单步调试理解陌生代码库的资深 Java 测试工程师，而并非一上来就扮演"DDD 专家"；目的也刻意收窄——在正式用 strategic design 拆子域之前，先不碰"子域"这种抽象概念，只做一件事：把 `commons-csv` 现有的行为摸透、建立具体手感。背景部分我给了它一段真实的维护者需求原文——要给 `CSVFormat.Builder` 加一个 `setRequiredHeaders(String...)`，让表头缺列能在读第一条记录之前就报清楚的错，而并非等业务代码调用 `record.get("currency")` 时才报一句"字段找不到"——目的只是让 Agent 知道"接下来要改的功能和表头有关"，并没有要求它这次就动手实现这个新功能。任务步骤分五步：先读需求原文和 `CSVFormat`、`CSVParser`（尤其 `createHeaders()`）、`CSVRecord`、`DuplicateHeaderMode` 的源码；再列一份不限数量的端到端场景清单；从里面挑出和"表头/必需列"直接相关的代表性场景；为挑出的场景写 JUnit 5 特征测试并真的跑通（反复强调只验证现有行为，故意不实现新功能）；最后把每个测试对应的断点位置、值得观察的变量、以及未来新需求可能插入的候选位置，整理成一份单步调试指南。输出要求也卡得比较死：全文中文，每条结论都要有源码行号或实测结果背书，证据不足必须标注"推测"，而且在没有真的跑通 `mvn test` 之前，不能在指南里断言某个测试"会通过"。

热身提示词一发出去，Agent 先自己核查了一轮事实（确认工作目录下已有 `./commons-csv`，HEAD 和源仓库一致、工作区干净；记录 JDK 21/Maven 3.9.16 和 `pom.xml` 里 `source/target=1.8` 的编译级别；后台启动全量基线测试），然后只问了 Round 0 的一个问题：**这三份产出到底是我自己的工作底稿，还是可以直接进书/课程章节的素材**——这决定了篇幅取舍、要不要为陌生读者解释背景、踩坑要不要提炼成"读者也会踩的坑"。它给了三个选项——纯自用底稿、章节素材、两者兼顾——自己推荐"兼顾"：证据先行（每个结论都有源码行号/测试输出背书），但不为了教学美观删减或润色掉真实发生的细节。我同意了这个选择。

这轮回复里我还确认了几件事：这批特征测试将来要当"不可变的回归安全网"（而非允许被后续新功能有意改写）；场景只覆盖"表头/列名/取值"这条主线，不铺开到分隔符/引号/转义等格式解析行为；全量基线我自己已经验证过是全绿的；本机 JDK/Maven 版本是否兼容，让 Agent 自己去查。

确认这些之后，Agent 补上它自己查到的事实（构建兼容性、`createHeaders()` 的精确行号、`DuplicateHeaderMode` 的三个取值等），一次性抛出 5 个问题：12 个代表性场景要不要增删、测试代码该用单文件 4 个 `@Nested` 分组还是拆成多个文件、踩坑记录放在调试指南末尾还是单独开文件、`setRequiredHeaders` 未来插入点的分析要不要摆出多个候选再对比、异常断言要精确到消息全文还是只断言类型 + 关键片段。这 5 个问题我都同意了它的建议——没有像子域分析那样出现需要我纠正的地方，这一轮走得比较顺。

### 产出：场景清单、调试指南、18 个特征测试

问题前沿清空后，Agent 产出了两份文档：

- **场景清单**（`ch02-1-2-scenarios-for-warming-up.md`）：列出 21 个和表头/必需列相关的场景（12 个会真的写测试、9 个只记录不测），按表头来源、按名取值边界、重复/空白列名、required 匹配语义相关的边界情况四组归类，并给出场景与测试方法的对应表。
- **调试指南**（`ch02-1-3-debug-guide.md`）：开头给出复制即用的命令，正文按测试类的 4 个 `@Nested` 分组逐个测试方法给出断点位置（类名+行号+该行代码）、要观察的变量、以及这个变量为什么能验证对应行为；第 3 节专门列了 3 个候选插入点（`CSVFormat.validate()`、`CSVParser.createHeaders()` 内、`CSVParser` 构造函数内）逐一对比，推荐落在 `CSVParser.createHeaders()` 末尾、`return new Headers(...)` 之前（`CSVParser.java:682` 之前）——这里是表头三种来源（无表头、自动探测、手工指定）唯一的汇合点，又天然在任何数据记录被读取之前执行。文末附一张行号对照表和一节"真实踩坑记录"（P1 到 P8）。

这两份文档背后是真实写出并跑通的测试代码：`kata` 包下新增 1 个 JUnit 5 特征测试类 `HeadersCharacterizationTest`，内含 4 个 `@Nested` 分组——`HeaderSources`（6 个方法）、`NameAccessBoundaries`（5 个方法）、`DuplicateAndBlankHeaders`（5 个方法）、`RequirementAdjacent`（2 个方法）——共 18 个 `@Test`，282 行，已经公开在 [`commons-csv-by-opencode-v2-with-glm-5.3`](https://github.com/wubin28/commons-csv-by-opencode-v2-with-glm-5.3) 仓库的提交 [`24562da2`](https://github.com/wubin28/commons-csv-by-opencode-v2-with-glm-5.3/commit/24562da2fff56fefd61ec8f6ce352632fb301957) 里。这些测试只验证 commons-csv **今天已有**的行为，故意不实现 `setRequiredHeaders`——那是留给后面章节做 TDD 的事。

### 可信怎么实现的

这批测试和两份文档的可信度并非靠"读起来像专业文档"，而是靠几件可以直接复核的事：**18 个测试一次全绿，没有出现断言和实测打脸的情况**——这一点和我自己原本设想"热身总会撞上几次预期落空"不太一样；但设计阶段确实有一次"预判偏差"：Agent 最初以为重复表头的校验只在 parse 时这一个时机检查，而实测发现手工表头在 `builder.get()`（配置期）就会抛，文件表头要等到 `format.parse()`（读入期）才抛——这个偏差被 `C1a`/`C1b` 两个测试分别钉住，而并非笼统合并成一条断言。另外还有几个 Agent 真实踩过的坑：用 `-Dtest` 过滤 `@Nested` 分组时，外层类那一行会显示"Tests run: 0"，乍看像没跑到测试，实际要看最后 `Results:` 的汇总；空文件加自动探测表头时，`headerMap` 是一个空 Map 而非 `null`，如果新校验只判 `null` 会漏掉这种"全缺"的边界情况。这些坑都被原样记录进调试指南的"真实踩坑记录"一节。全量 `mvn test` 从基线 **985 个测试**跑到 **1003 个、0 失败、0 错误、11 跳过**，这个数字本身也是可以在你自己的环境里重新跑一遍去验证的。

### 是否一把过

这一次我的体会是比下面的子域分析那一轮更顺：一个 Round 0 问题加 5 个编号问题，一轮就问完、前沿清空，而且我没有否决 Agent 的任何一条默认假设或建议。真正动手之后也没有出现"测试断言被实测结果打脸、需要回头改"的情况——18 个测试第一次跑就全绿。唯一能算"返工"的，是 Agent 在设计阶段那次"预判重复表头校验只有一个时机"的偏差，但那是后来 Agent 在写测试之前被它自己发现、直接写成两个分别命中两个时机的测试用例。这些都是 Agent 自动完成的，并非它先写错了然后我再手工修改提示词重做。

## 2.2 用 DDD 的 strategic design 快速理解陌生代码库并分清主次

<a id="ch2-def"></a>

#### 定义

Strategic Design 是 [《Learning Domain-Driven Design》](https://www.oreilly.com/library/view/learning-domain-driven-design/9781098100124/)（Vlad Khononov 著）第 1～4 章系统阐述的一套分析方法，核心是把一个业务域（business domain）拆解为若干子域（subdomain）——围绕同一批数据、同一批参与者、彼此紧密关联的一组用例集合——再根据"是否提供竞争优势""业务逻辑复杂度""波动性"三个维度，把每个子域归类为核心子域（core subdomain，公司区别于竞争对手的地方，必须自建、持续演进）、通用子域（generic subdomain，所有人都用同样方式做的事，应该买/用现成方案）或支撑子域（supporting subdomain，业务逻辑简单、没有竞争优势、但又没有现成方案可用，只能自建但不需要最优秀的人）。严格意义上的 strategic design 面向的是公司和团队，但这套分析工具同样可以类比映射到一个纯技术性的代码库上——把"库要解决的问题本身"当作业务域，把"这部分代码历史上改动、修 bug 的频率"当作波动性，借此快速建立对陌生代码库的心智模型。

<a id="ch2-value"></a>

#### 价值

对棕地项目维护者来说，strategic design 最直接的价值是把"这个代码库到底哪里重要、哪里不重要"这个判断,从"读代码读得越多、感觉越对"的模糊直觉，变成一套可追溯、可复用的分析方法——识别出哪些类是"牵一发而动全身"的核心业务逻辑，哪些类是"换一个现成方案也无所谓"的边角配置，再根据业务职责判断一个新需求真正会落在哪个子域、哪些类，而不会被"这个方法挂在哪个类的 API 上"这个表面现象误导。

<a id="ch2-risk"></a>

#### 没有它的危害

没有这套分析工具时，理解一个陌生棕地代码库往往只能靠"从 main 方法或者某个入口类开始，顺着调用链慢慢读下去"，容易把"代码行数多、方法名花哨"误判为"这里很重要"，或者反过来，漏掉一个代码行数很少但真正承载着核心业务规则的类。更危险的是，在拆分新需求的改动范围时，如果没有先划清子域边界，很容易把一个本该只改一两个类的小需求，稀里糊涂地改成牵动好几个不相关模块的大改动——这正是本书第 1.1 节说的"棕地项目返工代价成倍放大"的典型成因之一。

<a id="ch2-strength"></a>

#### 独特优势

strategic design 提供了一套**与代码行数无关、只看业务规则复杂度**的分类标准，这恰好是 Agent 辅助编程场景里最容易被忽视的一点——Agent 很擅长"读懂一段代码在语法上做了什么"，但不一定天然具备"这段代码在业务上有多重要"的判断力，而后者恰恰是人在评审 Agent 产出时最该把关的地方。用 strategic design 的框架去追问 Agent（"这个子域提供竞争优势吗？复杂度高不高？"），能逼着 Agent 给出有理由、可追溯的判断，而并非一句笼统的"这个类很重要"。

<a id="ch2-weakness"></a>

#### 主要劣势

strategic design 原本是为公司和团队设计的分析工具，用在一个单一团队维护的技术库上是一次"方法论改造"——子域之间的协作关系，严格意义上该用本章末尾提示词中的书摘中的 Ch.4《Integrating Bounded Contexts》里"partnership / shared kernel / conformist / anticorruption layer / open-host service"这些描述**不同团队**整合关系的模式来说明，但技术库内部的子域往往生活在同一个 bounded context 里，这些模式在这里只能作比喻使用，不能按字面意义套用，使用时需要明确声明这一点，避免误导读者以为这是严格的教科书式用法。

<a id="ch2-fit"></a>

#### 适用场景

接手一个陌生的、体量中等（几十到大几百个类）、职责边界相对清晰的棕地代码库，需要在动手改动之前，先建立起"哪里是核心逻辑、哪里是边角配置"的心智模型；尤其适合在"一个新需求挂在某个支撑子域的 API 上，但真正的业务规则其实该落在核心子域里"这类容易被表面现象误导的场景。

<a id="ch2-nofit"></a>

#### 不适用场景

业务逻辑单一、简单且代码库体量极小，几个类就能全部读完（这种情况下，"子域"这个分析单元本身意义不大，不如直接读代码）；此外，如果团队本身就是多团队协作、跨 bounded context 的大型系统，Ch.4 的整合模式应该按字面意义严格使用，而并非作为比喻。

## 2.3 识别核心、通用与支撑子域

> [!NOTE]
> 从这里到本章"动手练习提示词"之间所展示的内容，就是我在添加新功能之前“理解代码所承载的复杂业务逻辑”时与 OpenCode V2 搭配 GLM 5.3 用"假设体检 + 追问"提示词共创出来的过程与产出要点（原产出内容较长，你应该没有耐心读完，所以这里只展示精华）。你可以先快速浏览，然后复制本章后半部分的[动手练习提示词](#ch2-hands-on)给你的 Agent ，自己动手跑一遍，再回来和本章上述所展示的我的亲身体验内容对比复盘，看看自己的产出有什么差异、这些差异是否合理。

> [!IMPORTANT]
> 上述本章所展示的内容，都经过我本人验证。由于大模型的不确定性，你把本章末尾的"动手练习提示词"发给自己常用的 Agent 和大模型组合后，会看到不完全相同的产出——这是很正常的现象。所以上述展示的我的亲身体验内容，仅供你参考，而并非唯一答案。条条大路通罗马，解决问题的答案会有很多种。只要你理解了这份经过评审的参考结果背后的底层逻辑，再带着这份理解去评判你的 Agent 产出是否做到了"让 Agent 一次生成可信代码"，就已经能在亲身实践中有所收获。后面章节的相应的动手实操中展示的我的亲身体验的性质与之类同，不再赘述。

### 过程：Agent 问了什么、我怎么答、哪里猜错了

这份提示词我让 Agent 扮演资深 Java 架构师兼 DDD strategic design 教练，目标是在后续做"棕地新增需求"练习之前，先帮我把 commons-csv 这个陌生库的心智模型搭起来：产出两份文档——子域识别文档 SUBDOMAINS，以及新需求影响分析文档 IMPACT_ANALYSIS（这里要分析的新需求是给 `CSVFormat.Builder` 新增一个 `setRequiredHeaders`）。判断每个子域是 core、generic 还是 supporting，我没让它只给一句结论，而是要求逐一走竞争优势类比、复杂度、波动性、能否外包/用现成方案替代这四个维度，把"怎么判断出来的"讲清楚；波动性这一项，只要能访问 git log 就要求它去实测验证，而并非凭代码读起来的印象推断。

子域分析提示词发出去之前，Agent 先自己核查了一批"属于它自己职责"的事实（场景清单 `ch02-1-2-scenarios-for-warming-up.md` 已经存在、生产代码一共 12 个 `.java` 文件、当前 HEAD 和场景文件的锚点之间只差一个新增的测试文件、git 历史完整可查可以实测波动性），然后只问了 Round 0 的一个问题：**后续"棕地新增需求"这个练习，到底是谁、以什么形态做**——是 Agent 自己在这个仓库里动手实现 `setRequiredHeaders`、一场多人共读的工作坊、一次纯分析不动代码的练习，还是给其他同学核对答案用。它根据仓库里刚新增的特征测试这个信号，推荐"Agent 自己动手实现、兼容工作坊"这个选项，并说明这会让 IMPACT_ANALYSIS 文档第 6 节保持"零剧透"（只摆权衡、不给倾向答案）。我同意了这个判断，并顺带把几件背景事实答给它：这批特征测试将来是"不可变的回归安全网"；这两份文档是为后续用 TDD 实现新需求做准备；篇幅居中即可；需要实地跑 `mvn` 测试佐证行为结论。

这些回答解锁了 4 个新的决策点，Agent 一次性问完：子域划分粒度要粗（3 个）、中（4-5 个）还是细（6 个以上）；IMPACT_ANALYSIS 第 6 节除了按模板列开放设计问题，要不要再加一张"设计抉择 ↔ 验收测试必须断言什么"的映射表；`mvn` 实测要做到什么程度（全量跑一次当基线 + 针对性验证，还是每条结论都单独验证一次）；要不要在文档末尾附一张给"实现 agent"用的导航锚点表。这一轮我都直接同意了它的建议——没有出现需要我纠正默认假设的地方，这一轮问得很顺。

### 产出：5 个子域、哪个核心哪个通用哪个支撑、靠什么证据分出来的

问题前沿清空后，Agent 给我产出了文档 SUBDOMAINS （`ch02-2-2-subdomains.md`），把 commons-csv 这 12 个生产类（11 个真实类型 + 1 个纯文档性质的 `package-info.java`）收敛成 **5 个子域**：①格式契约（`CSVFormat` 及其内部 `Builder`/`Predefined`、`QuoteMode`、`DuplicateHeaderMode`、`Constants`，判定 **Core**）、②解析编排与表头/记录语义（`CSVParser`、`CSVRecord`，判定 **Core**）、③词法读取机制（`Lexer`、`Token`、`ExtendedBufferedReader`，判定 **Generic**）、④格式写出编排（`CSVPrinter`，判定 **Supporting**）、⑤错误词汇（`CSVException`，判定 **Supporting**）。每一条判定它都按"竞争优势类比／复杂度／波动性／能否外包替代"四个维度写了依据给我看，波动性这一项它并非凭印象下结论，而是真的跑了 `git log --oneline` 数出 `CSVFormat.java` **447** 次提交（含 132 次修 bug/JIRA 关键词的提交）、`CSVParser.java` **285** 次（77 次）、`CSVPrinter.java` 165 次、`Lexer.java` 121 次、`CSVRecord.java` 120 次、`ExtendedBufferedReader.java` 83 次——我看到这组数字直接支撑了"格式契约和解析编排是核心、词法机制虽然同样复杂但没有竞争优势"的判断。文档里它还专门留了一段声明：把"库"类比成"业务域"这件事本身只是一个分析假设，并非事实，这个类比最大的失真在于库的"战略"是由维护者社区对采纳度的追求隐性决定的，而并非企业的商业战略漂移。

这份文档还解释了一个我一开始也会犯的错：人们最容易把"技术难度最高、代码量最大"的部分判成核心——在 commons-csv 上具体会表现为把 `Lexer`（552 行，引号/转义/注释/多字符分隔符的状态机）误判成核心。但按"竞争优势类比"这条标准，`Lexer` 做的是 RFC 4180 这种公开规范驱动的通用活，每个同类库都有等价实现，用户不会因为这个词法器写得更好而选 commons-csv；真正的核心是"声明式方言契约"（格式契约子域）和"按名访问的容错语义"（解析编排子域）——这两者才是这个库"选它而不选手写 `split()` 或其他库"的理由。`CSVFormat.java` 3369 行里，约 600 行是已废弃的 `with*` 家族历史兼容代码，如果按行数加权，反而会把最不该投入精力的历史负担误判成核心。

这份子域分析引用了热身阶段真实产出的测试代码：`kata` 包下新增的 `HeadersCharacterizationTest`，18 个 `@Test`，282 行，已经合并进公开仓库的提交 [`24562da2`](https://github.com/wubin28/commons-csv-by-opencode-v2-with-glm-5.3/commit/24562da2fff56fefd61ec8f6ce352632fb301957)。这些测试我只验证了 commons-csv **今天已有**的行为，故意没有实现 `setRequiredHeaders`——留给后面章节做 TDD。

### 可信怎么实现的

子域判定在我看来站得住，并非因为 Agent "读起来觉得合理"，而是靠三类真实证据：（1）它真的通读了全部 12 个生产 `.java` 文件，而不只看类名猜职责；（2）凡是"波动性"这类可以实测的结论，它都真的跑了 `git log --oneline` 数出每个文件的提交次数去确证给我看，而并非凭印象下结论；（3）两张 Mermaid 依赖图上的每一条箭头，都标注了触发它的具体方法调用和源码行号（比如"`parse() 创建 (:2207)`"），而并非泛泛画一条线——这意味着图背后对应的是可以在 IDE 里逐条核对的真实调用关系，而非凭感觉画出来的示意图。

## 2.4 新需求实现的影响分析

### 过程：围着"这个需求到底牵动谁"反复确认

影响分析和子域识别是同一份提示词、同一场对话产出的，所以 Round 0 关于"这次练习到底是谁、以什么形态做"的那个问题，同样决定了影响分析第 6 节该留白到什么程度。确定"我自己动手实现、兼容工作坊"之后，Agent 没有直接给结论，而是先按我的要求**实地读代码**回答了"今天表头相关的校验分别发生在哪"：手工表头的重复列名在 `CSVFormat.validate()`（配置期）；文件表头的重复列名和空/空白列名在 `CSVParser.createHeaders()`（读入期）；按名访问找不到列、无映射、索引越界分别在 `CSVRecord.get(String)`（都是晚失败）；表头列数不等于数据列数在 `CSVRecord.isConsistent()`（被动查询，不抛）；配置自身的自洽性校验在 `CSVFormat.validate()`——一共 8 条现状逐条列出发生的类/方法、时机、抛出的异常类型和消息。

真正留给我决策的是 Round 1 的 4 个问题（子域划分粒度、要不要加"设计抉择↔验收测试映射表"、`mvn` 实测要做到什么程度、要不要给实现 agent 附一张导航锚点表），都是在 Round 0 定了调之后才能问的，我也都同意了建议。

### 产出：一条反直觉的结论、一张改动清单、6 个留白问题

IMPACT_ANALYSIS 文档（`ch02-2-3-impact-analysis.md`）让我最想讲清楚的一条结论是：**"需求挂在哪个类的 API 上"不等于"业务规则该落在哪个子域"**。需求字面上说"给 `CSVFormat.Builder` 加一个方法"，我的第一反应也是只改 `CSVFormat`；但真正的业务规则（"缺列必须在读第一条记录前报错"）必须落在②解析编排与表头/记录语义子域的 `CSVParser.createHeaders()` 里——因为表头三种来源（无表头、自动探测、手工指定）只在这个方法里汇合，①格式契约子域的 `validate()` 在 build 期根本看不到文件内容，对最常见的"自动探测表头"用法完全无效。这恰好和现状里"重复列名校验分居配置期与读入期两处"是同一个结构。文档据此给我列出了逐类改动清单：`CSVFormat` 新增 `requiredHeaders` 字段、`Builder.setRequiredHeaders()`、getter 以及 `equals`/`hashCode`/`toString`/复制链；`CSVParser.createHeaders()` 末尾新增必需列检查；`CSVRecord` 代码不改，其"晚报错"路径作为安全网原样保留；`CSVPrinter`、`Lexer`、`Token`、`ExtendedBufferedReader`、`CSVException` 等按"改/不改/视选择"逐一标注。

#### 时序图（新增检查步骤插在哪一步）


**新增步骤位置**：`createHeaders()` 末尾、`return new Headers(...)` 之前（源码 L682）。它**先于**任何数据记录的返回（`nextRecord()` 在迭代期才被再次调用）。

文档末尾留了 6 个没有标准答案的开放设计问题：异常类型该复用 `IllegalArgumentException` 还是改用 `CSVException`、必需列名和实际表头的匹配语义（精确匹配/trim 后匹配、是否跟随 `ignoreHeaderCase`、命中重复表头时取哪个索引）、校验时机是只在读入期统一校验还是也给手工表头在配置期提前校验、新校验和既有的空列名/重复列名校验谁先谁后报错、写方向的 `CSVPrinter` 要不要对称校验、配置矛盾（设了必需列却没配表头）和空文件场景该怎么处理——每个问题都只写清楚"权衡点是什么"，不给我自己的倾向，还额外配了一张"设计抉择 ↔ 验收测试必须断言什么"的映射表，留给读者在第三章用决策表把它们一个个裁决掉、落成验收测试。

### 可信怎么实现的

这份影响分析的可信度，在我看来建立在它和子域识别用的是**同一套实测证据**：现状校验的类名、方法名、行号、精确异常消息，全部来自前面"实地读代码+实跑既有测试"验证过的事实报告（全量 `mvn test` 1003 例全绿，外加针对性复跑 `CSVDuplicateHeaderTest` 348 例、`CSVRecordTest` 33 例、`HeadersCharacterizationTest` 18 例全绿），而并非另起一套凭印象写的说明。文档还帮我特别验证了一致性——新需求的裂缝和"重复列名现状分居两处"的裂缝是同构的，这个类比本身就是一种交叉校验：如果影响分析得出的结论和已经验证过的现状规律自相矛盾，就说明判断错了。

### 是否一把过

我的体会同样是并非零迭代，但没有返工：Round 0 的 1 个问题加 Round 1 的 4 个编号问题问完，文档一次成型，没有出现"结论写完又推翻重写"的情况。这一轮我没有纠正 Agent 的任何默认假设，也没有发现需要公开更正的事实性错误——相比子域识别阶段那次"预判重复表头校验时机"的偏差，这一轮走得更顺。

## 2.5 动手练习提示词

````
## 附录：DDD Strategic Design 参考摘要

以下内容是《Learning Domain-Driven Design》（Vlad Khononov 著）第 1–4 章要点的概括整理，帮助你理解"为什么要先弄清楚表头相关的现有行为，而并非其他代码"——你暂时不需要用它做子域判定，只需要理解"核心子域的业务规则，往往就是最值得优先用测试和单步调试搞清楚的那部分代码"这个背景。

### 第 1 章《Analyzing Business Domains》要点

- **业务域**（business domain）：公司提供给客户的主要服务领域。公司要在业务域里成功，需要同时运作在多个**子域**（subdomain）——更细粒度的业务活动单元，彼此协作才能支撑整体业务。
- **核心子域（core subdomain）**：公司区别于竞争对手的地方——可能是发明新产品/服务，也可能是优化已有流程来降低成本。核心子域天然复杂（简单的东西很快会被竞争对手抄走），需要高准入门槛，要求公司自己投入最优秀的人、用最先进的工程手段**自建**，而且会持续演进（不存在"做完了"的核心子域）。判断一个子域是不是核心的小技巧：问自己"这个子域能不能单独拿出来做成一家公司，别人会不会为它单独付钱？"——能，就是核心子域。
- **通用子域（generic subdomain）**：所有公司都用同样方式在做的事情（比如身份认证）。同样复杂、同样难，但**不提供任何竞争优势**——已经有久经考验的现成方案，没必要自己发明，策略上应该"买/用开源方案"而并非自建。
- **支撑子域（supporting subdomain）**：业务逻辑简单（基本就是数据录入界面和 ETL/CRUD 操作），不提供竞争优势，但公司运转离不开它，又没有现成的通用方案可以直接用，所以只能自己写，可以外包或交给新人练手，不需要用最先进的工程技术。
- 三者对比（竞争优势 / 复杂度 / 波动性 / 实现策略）：

  | 类型 | 竞争优势 | 复杂度 | 波动性 | 实现策略 |
  | --- | --- | --- | --- | --- |
  | Core | 有 | 高 | 高 | 自建，最优秀的人 |
  | Generic | 无 | 高 | 低 | 买/用现成方案 |
  | Supporting | 无 | 低 | 低 | 自建/可外包 |

- **重要提醒**：核心子域不一定是"技术性"的（比如可能是珠宝设计这种和代码无关的事）；反过来，判断"软件相关的核心子域"时，要看**要实现的业务逻辑复杂度**——是像数据录入/CRUD 一样简单，还是需要实现复杂算法/被复杂业务规则和不变式编排的流程？前者是支撑子域的信号，后者才是核心子域的信号。**代码量大小并非判断标准**，业务逻辑的复杂度才是。
- **如何找子域边界**：从公司部门这种粗粒度单元开始，但往下细挖（distill），直到找到"一组围绕同一批数据、同一批参与者、彼此紧密关联的用例集合"——这就是子域的精确边界（"subdomains as coherent use cases"）。核心子域要尽量挖得精细（因为它最重要、最该聚焦投入）；通用/支撑子域如果继续往下挖不能带来新的设计决策信息，就可以停止。
- **域专家（domain experts）**：对业务领域了如指掌的人，通常是提出需求的人或软件的最终用户，既非分析师，也非工程师。

### 第 2 章《Discovering Domain Knowledge》要点

- **ubiquitous language（通用语言）**：让所有相关方（域专家、工程师、产品等）用同一种语言描述业务领域，避免"翻译链"（业务知识 → 分析模型 → 需求 → 设计 → 代码，每一步都会失真）。
- 这门语言必须是**业务语言**，不含技术术语（不说"iframe 显示 HTML"，而说"广告位展示创意素材"）。
- 语言必须**一致**：每个术语只能有一个含义，不能有歧义或同义词并存。
- 这个语言只在**特定边界内**保持一致（这就引出了第 3 章的 bounded context）。

### 第 3 章《Managing Domain Complexity》要点

- 当同一个术语在不同部门/场景下有不同含义（比如"lead"在市场部和销售部的含义不同）时，不能强行用一个模型覆盖所有场景，而要把通用语言拆分成多个更小的语言，每个语言只在自己的**bounded context（边界上下文）**内保持一致。
- **bounded context 是被设计出来的，subdomain 是被发现出来的**：子域是业务本来就存在的结构（不管你写不写软件，业务都是按这些子域运作的）；bounded context 是工程师为了实现软件系统主动做的设计决策（怎么划分模型边界、怎么划分团队和物理部署单元）。
- 一个 bounded context 可以只对应一个子域，也可以装下好几个子域（这完全取决于设计决策，并非固定规则）。但不要把"一个内聚的功能"硬拆到多个 bounded context 里，否则会导致本该一起变化的东西被迫分别维护、分别发布。
- bounded context 同时是**模型边界**、**物理部署/技术栈边界**、和**团队所有权边界**（一个 bounded context 只能由一个团队负责，但一个团队可以负责多个 bounded context）。

### 第 4 章《Integrating Bounded Contexts》要点

- **cooperation（合作类，团队间沟通顺畅时用）**
  - *Partnership（伙伴关系）*：两个团队非正式地协调集成，谁改了接口就通知另一方，双方一起解决集成问题。
  - *Shared kernel（共享内核）*：多个 bounded context 共用同一份模型/代码，任何改动必须同步触发所有相关方的集成测试。
- **customer–supplier（客户-供应商类，上下游团队可以独立成功，存在权力不对等）**
  - *Conformist（随从者）*：下游完全接受上游的模型，不做任何转换。
  - *Anticorruption layer（防腐层，ACL）*：下游不愿意接受上游模型，自己写一层转换，把上游模型翻译成适合自己的模型。
  - *Open-host service（开放主机服务）*：上游主动把"对外发布的接口模型"和"内部实现模型"解耦，设计一套专门给消费者用的、稳定的"published language"。
- **separate ways（分道扬镰，不集成，各自重复实现）**：当团队间沟通成本太高、或者要集成的是一个"集成成本比重复实现还贵"的通用子域时，宁可各自重复实现，也不集成。**核心子域不应该用这个模式**。
- **context map（上下文地图）**：把所有 bounded context 和它们之间用的整合模式画成一张图，给出系统的高层设计、团队协作模式、以及潜在组织问题的洞察。
````

````
## 4.9 附录：DDD Strategic Design 参考摘要

以下内容是《Learning Domain-Driven Design》（Vlad Khononov 著）第 1–4 章要点的概括整理，是你完成上面任务需要用到的全部 DDD 背景知识，不需要额外查阅其他资料。

### 第 1 章《Analyzing Business Domains》要点

- **业务域**（business domain）：公司提供给客户的主要服务领域。公司要在业务域里成功，需要同时运作在多个**子域**（subdomain）——更细粒度的业务活动单元，彼此协作才能支撑整体业务。
- **核心子域（core subdomain）**：公司区别于竞争对手的地方——可能是发明新产品/服务，也可能是优化已有流程来降低成本。核心子域天然复杂（简单的东西很快会被竞争对手抄走），需要高准入门槛，要求公司自己投入最优秀的人、用最先进的工程手段**自建**，而且会持续演进（不存在"做完了"的核心子域）。判断一个子域是不是核心的小技巧：问自己"这个子域能不能单独拿出来做成一家公司，别人会不会为它单独付钱？"——能，就是核心子域。
- **通用子域（generic subdomain）**：所有公司都用同样方式在做的事情（比如身份认证）。同样复杂、同样难，但**不提供任何竞争优势**——已经有久经考验的现成方案，没必要自己发明，策略上应该"买/用开源方案"而并非自建。
- **支撑子域（supporting subdomain）**：业务逻辑简单（基本就是数据录入界面和 ETL/CRUD 操作），不提供竞争优势，但公司运转离不开它，又没有现成的通用方案可以直接用，所以只能自己写，可以外包或交给新人练手，不需要用最先进的工程技术。
- 三者对比（竞争优势 / 复杂度 / 波动性 / 实现策略）：

  | 类型 | 竞争优势 | 复杂度 | 波动性 | 实现策略 |
  | --- | --- | --- | --- | --- |
  | Core | 有 | 高 | 高 | 自建，最优秀的人 |
  | Generic | 无 | 高 | 低 | 买/用现成方案 |
  | Supporting | 无 | 低 | 低 | 自建/可外包 |

- **重要提醒**：核心子域不一定是"技术性"的（比如可能是珠宝设计这种和代码无关的事）；反过来，判断"软件相关的核心子域"时，要看**要实现的业务逻辑复杂度**——是像数据录入/CRUD 一样简单，还是需要实现复杂算法/被复杂业务规则和不变式编排的流程？前者是支撑子域的信号，后者才是核心子域的信号。**代码量大小并非判断标准**，业务逻辑的复杂度才是。
- **如何找子域边界**：从公司部门这种粗粒度单元开始，但往下细挖（distill），直到找到"一组围绕同一批数据、同一批参与者、彼此紧密关联的用例集合"——这就是子域的精确边界（"subdomains as coherent use cases"）。核心子域要尽量挖得精细（因为它最重要、最该聚焦投入）；通用/支撑子域如果继续往下挖不能带来新的设计决策信息，就可以停止。
- **域专家（domain experts）**：对业务领域了如指掌的人，通常是提出需求的人或软件的最终用户，既非分析师，也非工程师。

### 第 2 章《Discovering Domain Knowledge》要点

- **ubiquitous language（通用语言）**：让所有相关方（域专家、工程师、产品等）用同一种语言描述业务领域，避免"翻译链"（业务知识 → 分析模型 → 需求 → 设计 → 代码，每一步都会失真）。
- 这门语言必须是**业务语言**，不含技术术语（不说"iframe 显示 HTML"，而说"广告位展示创意素材"）。
- 语言必须**一致**：每个术语只能有一个含义，不能有歧义或同义词并存。
- 这个语言只在**特定边界内**保持一致（这就引出了第 3 章的 bounded context）。

### 第 3 章《Managing Domain Complexity》要点

- 当同一个术语在不同部门/场景下有不同含义（比如"lead"在市场部和销售部的含义不同）时，不能强行用一个模型覆盖所有场景，而要把通用语言拆分成多个更小的语言，每个语言只在自己的**bounded context（边界上下文）**内保持一致。
- **bounded context 是被设计出来的，subdomain 是被发现出来的**：子域是业务本来就存在的结构（不管你写不写软件，业务都是按这些子域运作的）；bounded context 是工程师为了实现软件系统主动做的设计决策（怎么划分模型边界、怎么划分团队和物理部署单元）。
- 一个 bounded context 可以只对应一个子域，也可以装下好几个子域（这完全取决于设计决策，并非固定规则）。但不要把"一个内聚的功能"硬拆到多个 bounded context 里，否则会导致本该一起变化的东西被迫分别维护、分别发布。
- bounded context 同时是**模型边界**、**物理部署/技术栈边界**、和**团队所有权边界**（一个 bounded context 只能由一个团队负责，但一个团队可以负责多个 bounded context）。

### 第 4 章《Integrating Bounded Contexts》要点（仅在你分析的子域确实跨越了不同团队/不同 bounded context 时才按字面意义使用，否则只能作比喻）

- **cooperation（合作类，团队间沟通顺畅时用）**
  - *Partnership（伙伴关系）*：两个团队非正式地协调集成，谁改了接口就通知另一方，双方一起解决集成问题。
  - *Shared kernel（共享内核）*：多个 bounded context 共用同一份模型/代码，任何改动必须同步触发所有相关方的集成测试；适用场景之一是"同一个团队维护多个 bounded context，用共享内核明确划出一个本该一起管理的公共契约"。
- **customer–supplier（客户-供应商类，上下游团队可以独立成功，存在权力不对等）**
  - *Conformist（随从者）*：下游完全接受上游的模型，不做任何转换。
  - *Anticorruption layer（防腐层，ACL）*：下游不愿意接受上游模型，自己写一层转换，把上游模型翻译成适合自己的模型——适用于下游是核心子域、或上游模型很糟糕/变化频繁的情况。
  - *Open-host service（开放主机服务）*：上游主动把"对外发布的接口模型"和"内部实现模型"解耦，设计一套专门给消费者用的、稳定的"published language"，即使内部实现经常变，published language 也可以保持稳定或支持多版本并存平滑升级。
- **separate ways（分道扬镰，不集成，各自重复实现）**：当团队间沟通成本太高、或者要集成的是一个"集成成本比重复实现还贵"的通用子域（比如日志框架）时，宁可在各自的 bounded context 里各写一份，也不集成。**核心子域不应该用这个模式**，重复实现核心子域会违背"集中精力把核心子域做到最好"的战略。
- **context map（上下文地图）**：把所有 bounded context 和它们之间用的整合模式画成一张图，给出系统的高层设计、团队协作模式、以及潜在组织问题的洞察。
````

提示词结束，以上内容请整段复制给 Agent。

</details>

跑完整个流程后，把你的 Agent 产出的两份文档，和本章 2.3～2.4 节逐节对比——尤其关注 Round 0 阶段它对你的诉求提出了什么追问、有没有把"代码行数多"误判成"业务逻辑复杂"，以及"开放设计问题"这一节是否漏掉了某个需求原文没写清楚、但实际核查代码后才会发现的交互点（比如在`ch02-2-3-impact-analysis.md`的开放问题中，很多人直接假设两种 CSV 表头模式行为一致，却懒得去代码里确认）。下一章会把这些开放问题逐一裁决，并用决策表的方法推导出完整的验收测试用例。

子域地图画清楚了，新需求该落在哪几个类也有了结论——但 `ch02-2-3-impact-analysis.md`留下的几个开放设计问题还悬在半空，不裁决就没法往下写验收测试。第三章会先用一份轻量 ADR 把这些问题逐一拍板，再用决策表测试法把裁决结果系统性地推导成一份不遗漏、不重复的验收测试用例清单，这是"设计"这一步要交付的东西。
